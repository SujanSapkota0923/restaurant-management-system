# Known Risks

Owner: `security-engineer` (security) and orchestrator (delivery). Accepted risks record who accepted them and when.

| # | Risk | Impact | Mitigation | Status |
|---|------|--------|------------|--------|
| R1 | RLS misconfiguration (table owner role, missing `FORCE`, missing policy on a new table) silently disables the DB backstop | Cross-tenant exposure | Non-owner app role; migration rule; CI test that every tenant table has RLS enabled+forced and a policy | Open — Phase 2 |
| R2 | Main session implements directly and skips gates | Unreviewed, unsafe changes | `CLAUDE.md` orchestrator rule; risk table; `retro` checks change records | Open |
| R3 | Requirements invented under time pressure | Wrong business behavior | Open-questions discipline; `requirements-analyst` boundary | Open |
| R4 | Stack not yet decided (ADR-0004 Proposed) delays Phase 2 | Schedule | Decide in Phase 1 | Closed — ADR-0004 accepted 2026-09-30 |
| R5 | Legacy `../rms` has committed secrets (`docker-compose.yml`) | If those values were ever used outside local dev, they are compromised | Never reuse | Closed — owner confirmed local-only use (2026-09-30) |
| R6 | Legacy code is partly unverified (commit messages indicate unchecked AI-generated changes) | Wrong patterns copied | ADR-0002: no copying without justification | Mitigated |
| R7 | Shared kitchen/POS devices blur audit attribution | Weak accountability | Device sessions (Q7); kitchen = device attribution by owner decision (C6.13); POS = individual via PIN switch (`security.md` PN-01..PN-11) or no order/payment codes on devices until PIN exists (DV-01) | Open — v1 POS approach decided: no counter/POS device profile in v1, orders and payments on personal devices (C6.17); PIN switch later |
| R8 | Payment and tax rules differ by market; fiscal compliance unknown | Legal/financial | Q1, Q14, Q15 answered before Phase 6 | Open |
| R9 | Network instability in restaurants | Lost or duplicated orders | Idempotency keys, pending states, reconnect/catch-up for kitchen (Q19) | Open — Phase 2/5 |
| R10 | Engineering system not yet exercised on a real change | Gaps discovered late | First Phase 2 change followed by `retro` | Open |
| R11 | Pre-tenant reads (login, restaurant switcher, invite acceptance) need a user's memberships across tenants; without a sanctioned path, implementers bypass RLS (0002 C3-1) | Cross-tenant exposure through an ad-hoc bypass | Single reviewed identity-scoped path (policy on `app.user_id` or reviewed definer function) | Open — mitigation accepted as design (ADR-0003 C3-1 a+c, 2026-09-30); implement and test in Phase 2 |
| R12 | Tests run as a DB superuser, so RLS is bypassed and every isolation test passes vacuously (0002 C3-7) | False assurance of isolation | Test runner connects as the app role; guard test on `current_user` privileges | Open — Phase 2 |
| R13 | Tenant context leaks or errors on reused/pooled connections (string-built `SET LOCAL`, session-level set, `''` after reset) (0002 C3-2/3/10) | Wrong-tenant queries or 500s that invite bypasses | `set_config(..., true)` with bound UUID; `NULLIF` in policy; connection-reuse test | Open — mitigation accepted as design (ADR-0003 C3-2/3/10, 2026-09-30); prove in Phase 2 spike |
| R14 | Single "active membership" in the session is shared across tabs; switching in one tab retargets writes from another (0002 C6-2, TM-09) | Orders/payments written to the wrong restaurant | Tenant resolved per request from the URL path, validated against memberships; 409 on mismatch | Open — mitigation accepted as design (ADR-0006 C6-1/C6-2, 2026-09-30); implement and test in Phase 2 |
| R15 | Long-lived realtime connections hold stale authorization and exhaust DB/worker capacity during service (TM-21/23) | Revoked staff keep seeing tickets; kitchen outage | Bounded stream lifetime, no transaction held by streams, per-membership caps, load test | Open — Phase 5 |
| R16 | Migration/owner credentials present in API or worker runtime (0002 C3-6, TM-29) | A compromised app process bypasses RLS | Separate migration job and credentials; CI check of runtime env | Open — mitigation accepted as design (ADR-0003 C3-6, 2026-09-30); implement in Phase 2 |
| R17 | Shared kitchen/POS devices run on a personal (possibly owner) session (0002 C6-7) | Standing privilege escalation, weak attribution (see R7) | Device session type with fixed limited permissions; pairing/revocation require `devices.manage` (C6.14); eligibility list DV-01 | Open — mitigation accepted as design (Q7 = yes, ADR-0006 C6-7; UX-5 answered by C6.14, 2026-09-30); catalog codes approved (C6.19), device-eligibility list still Proposed; implement in Phase 2 |
| R18 | Customer QR surface (Q11) would add an unauthenticated write path; legacy tokens never expired and were accepted from the query string | Order spam, fraud, token leak via logs | Separate threat model before Phase 5 if Q11 = yes | Open — deferred with Q11 |
| R19 | Manager-set staff passwords (C6.11): the manager knows or can reset a staff credential and can act as that person until it is changed | Impersonation; weak "who did it" (C5) | Forced change at first login, temporary-password expiry, never-view, audited reset that ends sessions, notice to the staff member (`security.md` SP-01..SP-08, TM-32) | Accepted by product owner 2026-09-30 (C6.23) |
| R20 | Admin password reset of an identity that also belongs to another restaurant, or staff creation adopting an existing identity | Cross-tenant account takeover | Reset only for tenant-managed identities; never adopt an existing identity; non-owners never reset owners (SP-07, SP-08, TM-33/35) | Open — rules decided by product owner 2026-09-30 (C6.16 reset scope, owners never reset by managers; C6.20 existing identities cannot be added as staff); implement and test in Phase 2/3 |
| R21 | PIN switch on shared POS: low-entropy secret, shoulder surfing, spraying across names, offline cracking after a DB leak | Wrong attribution of orders and payments; fraud | PIN only on a paired device, per membership, ≥ 6 digits, pick-then-PIN, throttling and disablement, peppered hash, device ∩ membership permissions (PN-01..PN-11, TM-38/39) | Open — not in v1 (C6.17); PIN length and throttle rules pending owner (Q81) |
| R22 | Pre-account hijacking through a manager-entered email that the manager does not own | Later owner or invitee inherits a credential the manager knows | Unverified email grants nothing; no staff email features in v1, so a staff email never receives a reset link or account email (C6.21); verification invalidating the previous password applies only if staff email verification is added later (SP-09, TM-34) | Open — Phase 2 design |
| R23 | Shared device sessions have no idle or absolute timeout (C6.12) | A copied or stolen device credential works until someone notices and revokes it | Server-side credential rotation, last-seen list, per-device revocation, stale-device flag (DV-03, DV-04, TM-44) | Open — rotation interval and any auto-revocation pending owner (Q82) |
| R24 | PWA/service-worker or client caches keep tenant data on shared devices after logout, switch-out or revoke | Next user sees previous user's data | No `/api/` caching in the service worker; `Cache-Control: no-store`; clear on logout, switch-out and revoke (TM-45) | Open — Phase 2 frontend baseline |
| R25 | Public health endpoints `/health/live`, `/health/ready` are not rate-limited (change 0003, T3) | Request flooding against the readiness DB check | Short DB connect timeout; no data returned; reverse-proxy rate limit in Phase 10 | Accepted by product owner 2026-10-01 until Phase 10 |
| R26 | `uvx` audit/lint tools (pip-audit, zizmor) pin only the top-level version; transitive deps float (0003 F5) | Supply-chain compromise of CI tooling | Exact top-level pins; follow-up: `--exclude-newer` or hashed tool requirements | Accepted by product owner 2026-10-01; fix as Phase 2 follow-up |
| R27 | `scripts/ci/check-workflows.sh` misses quoted or multi-line trigger syntax, e.g. `"issue_comment":` (0003 F7) | Comment/dispatch-triggered workflow runs unnoticed | zizmor catches `pull_request_target`/`workflow_run` in all forms; read-only token, no secrets; workflow changes reviewed; follow-up: allow only `{push, pull_request}` | Accepted by product owner 2026-10-01; fix as Phase 2 follow-up |
| R28 | GitHub repo settings (SC-38: required checks on `main`, fork-PR approval, read-only default token) not yet applied | CI advisory; unchecked merges possible | Owner applies settings from `docs/process/operations.md` before first merge to `main` | Open — owner action |
